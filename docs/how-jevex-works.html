A structured controller + a language model + real tools

Decisions here.
Words there.

Jevex separates deciding what an agent does from writing what it says. Jev directs the research. An LLM supplies the search text and the final explanation. Python executes the selected tools.

This explains the implemented prototype, not a proposed architecture. Follow one live Webb/Hubble investigation, then examine measured token usage and the cases where the design failed.

01 / THE SPLIT

One agent. Three distinct responsibilities.

In the native tool-calling baselines, the LLM sees a tool catalog, selects calls, constructs arguments, reads results, and eventually answers. Jevex moves action selection to Jev, TypeSafe’s structured-decision model. The writing model is invoked only for a specific content assignment.

Jev · controller

Choose the next move

Select a tool, choose the research question to pursue or URL to read, approve the proposed call, and decide when to answer or stop.

LLM · writer

Produce the content

Turn the assigned question into a search query. Later, turn supplied evidence into a cited brief. No tool catalog or native tool-call interface is provided.

Python + MCP · execution

Make the call real

Build and validate arguments, invoke an allowed external tool, cap the returned text, and append the result or error to shared state.

“No decisions by the LLM” means no control-flow authority. The writer still makes semantic choices when composing a query or answer; those choices affect quality. It does not select the next tool, schedule retrieval, or decide when the loop is done.

MCP is the tool connection protocol here—not another model. The Python client discovers tool descriptions and schemas from servers and uses those connections to execute calls. Jev and the LLM do not access the servers directly.

02 / THE CONTROL LOOP

The controller owns the agenda.

Structured choices, not action prose

Each Jev request contains current state, a decision instruction, and a finite map of candidate IDs to descriptions. The response identifies a choice and reports confidence/probabilities. Python maps that choice back to an action or candidate.

For URL selection, the adapter extracts URLs from the request and successful observations, removes common asset links and already-read pages, and presents up to 254 candidates plus “none.”

Approval is useful, but not proof

Before execution, Jev judges whether the fully constructed call is relevant and useful. Python separately checks the tool allowlist and JSON schema. A valid, relevant call can still return incomplete or misleading evidence.

Confidence is logged, not used as a minimum threshold in this read-only benchmark. Several next reads may be reasonable; confidence is not a guarantee of correctness.

What prevents the loop from running forever?

The default is ten action iterations. Exact duplicate tool/argument combinations are rejected. Argument-preparation or approval failures temporarily remove that action from the next choice set; the block set clears after a tool attempt. Execution errors enter observation history. Each tool call has a 45-second timeout. These are bounds and recovery mechanisms, not a guarantee of progress.

The “retrieve at least two pages before answering” rule is currently an instruction to Jev and a post-run check—not a hard gate that removes the answer action.

03 / A REAL RESEARCH RUN

Follow the Webb/Hubble investigation.

Compare Webb and Hubble for observing the early universe. Cover mirror sizes, wavelength capabilities, redshift, observing locations, and why Webb is not a universal replacement. Retrieve at least two primary-source pages and cite them.

Condensed from the actual brief. All three arms also receive the same three explicit research questions. They do not receive the evaluator’s expected fact patterns.

  1. Jev chooses search—and the gap to investigate.

    Initial state contains the brief, three research questions, and no events. Jev selects advanced search, then chooses the question about infrared sensitivity, redshifted early galaxies, and Hubble’s remaining capabilities. These are two separate Jev decisions.

  2. The LLM writes one query.

    The writer receives the brief and assigned question—not the tool name, schema, or alternative actions. It returns:

    site:nasa.gov OR site:esa.int Webb infrared sensitivity
redshifted early galaxies Hubble capabilities wavelength coverage

    Python adds numResults=5, textMaxCharacters=2500, enableSummary=False, and type="auto". Jev approves; Python validates and executes the Exa search. LLM call 1: 233 input / 94 output tokens.

  3. Jev selects and reads the first source.

    The search result enters state. Jev selects Exa page retrieval, chooses NASA’s Hubble vs. Webb page from known URLs, and approves the call. Python supplies the URL and a 12,000-character retrieval parameter. The LLM is not called.

  4. Jev selects a second source.

    With the first page in state, Jev selects retrieval again, chooses NASA’s How Can Webb Study the Early Universe?, and approves it. Again, no LLM call is needed to copy a known URL into an argument.

  5. Jev decides to answer. The LLM synthesizes.

    Jev selects answer. The writer receives the request and a content-only projection of the search result and two pages. It connects mirror sizes and wavelength coverage to redshift, observing location, and complementary capabilities, citing the two NASA pages. LLM call 2: 7,221 input / 820 output tokens.

04 / THE CONTEXT BOUNDARY

Shared evidence. Different views.

Shared state is a Python data structure, not a shared conversational memory inside both models. Each API call receives an explicitly constructed view. Jev gets the state needed to choose; the writer gets its assignment and content.

Controller view

“What should happen next?”

Request, research questions, events with tool identities, arguments, success/error status, and delivered results. Candidate descriptions are supplied for each decision; approval also includes the proposed call.

Writer view

“Write this particular thing.”

For a query: brief + assigned question. For synthesis: request + evidence entries containing source references and delivered content or retrieval errors. No tool schemas, action menu, or Jev decision transcript.

Not supplied: catalog, schemas, candidate choices, decision log.

The research writer currently receives all source-bearing observations at synthesis, including search output. This is not a claim-aware evidence selector or a compressed knowledge store. The per-call result cap limits individual observations, not total accumulated context.

This is an interface boundary, not a security sandbox. Tool metadata is omitted by construction, but retrieved text remains untrusted. Instructions tell both models to treat it as evidence rather than commands; the prototype does not establish production-grade prompt-injection resistance.
05 / A FAIR COMPARISON

Compare completed research, not just short runs.

The benchmark runs the same briefs through three architectures. All use the configured writing model, gpt-5.6-luna, the same four-tool catalog, and the same result/output limits. The Jev arm additionally uses jev-latest.

ArmWho controls actions?What the LLM sees
JevJev, with catalog-specific Python argument adapters.A query-writing assignment or final evidence-writing assignment. No tools bound to the model.
StandardThe LLM using native function calls.The catalog and accumulated conversation, including returned assistant messages and tool results.
CompactThe LLM using native function calls.The catalog and reconstructed tool-call/result history. Earlier assistant prose/reasoning is omitted; evidence remains.

The compact baseline matters: it tests whether the reduction is simply an advantage over a history-heavy implementation. It does not summarize or selectively retrieve old evidence. Reconstructed messages preserve actual assistant/tool roles.

Shared limits are ten action iterations, 2,000 LLM output tokens per call, and 12,000 characters per tool result. Text-form Exa search records are shortened individually to preserve discovery breadth. Baselines can batch-fetch URLs; the Jev adapter selects one URL per fetch. Same tools do not imply the same retrieval trajectory or equal numbers of model calls.

One repetition is a smoke test. The controller was developed on these three tasks. Arm order rotates, but there is no controlled cold-cache regime, held-out task set, or reliable estimate of accuracy and latency variance.
06 / COUNTING TOKENS

Less LLM work. Not necessarily lower total cost.

The strongest quality-qualified pair is Webb/Hubble: Jev and compact passed automated checks, with no recorded manual grounding failure. The standard arm failed citation provenance, so it is not a successful comparison pair.

Where the numbers come from

Meter wraps each LLM invocation and logs provider usage metadata. It sums every completed call, including generations later rejected or found empty. Missing usage raises an error rather than counting a call as free. Failed requests without usage can have unknown billing.

For Webb/Hubble, Jev added 44,061 input and 609 output tokens across ten controller calls. The LLM used 7,454 input and 914 output tokens across two calls. Wall time was 20.2 seconds for Jev versus 37.6 seconds for compact, excluding shared MCP startup. That is one observation, not a latency guarantee.

The reduction comes from fewer writer invocations, no catalog in writer prompts, and less repeated LLM processing of growing evidence. This experiment changes those together; it does not isolate the causal contribution of each.

How to turn usage into a cost model

Use the applicable rates for each provider and normalize their pricing units before multiplying:

total cost ≈ uncached LLM input × input rate
+ cached LLM input × cache rate
+ LLM output × output rate
+ Jev charges + retrieval charges + billable retries

Then account for satisfactory-answer probability and review or repair work. No dollar estimate is asserted here. A reduction in one model’s token count is not proof of an end-to-end saving.

07 / WHAT WENT WRONG

The controller can finish before the evidence does.

The evaluator checks expected fact patterns, at least two retrieved primary-source pages, at least two citation URLs, and whether citations were actually delivered as retrieved pages. For Exa batches, it checks visible page headers and sufficient body text; merely requesting a URL is not enough. These are heuristics—not semantic proof that a citation supports a claim.

Standard · Webb/Hubble

Requested ≠ delivered

The answer cited Webb’s orbit page. Its URL had been requested in a batch, but truncation removed its page body from delivered evidence. Citation provenance failed.

Jev · climate

Discovered ≠ retrieved

The answer cited a Copernicus PDF found in discovery material, but never fetched. Jev had read WMO’s report and a Copernicus methods page, then authorized synthesis without retrieving that PDF.

Jev · Bennu

Retrieved ≠ supported

The cited NASA page supported the count of fourteen amino acids, but the writer supplied a specific enumeration absent from delivered evidence. Automated checks passed; manual review failed it.

Do not count an incomplete answer as a saving. After automatic and recorded manual exclusions, there is one successful pair against compact and none against standard. Bennu is excluded despite passing automated checks.

The source-delivery checker was corrected after execution and reapplied to every saved run without new model calls. Original checks and traces were retained. The manual Bennu annotation is tied to this particular run.

What this suggests next—not implemented yet

  • Separate discovery from citable evidence. Pass explicit delivered-source IDs to the writer and enforce citation membership after generation.
  • Verify claims, not only URLs. Check whether each material claim is supported by the cited passage; a genuine source can still carry an unsupported claim.
  • Make completion evidence-aware. Track coverage of each question and route missing evidence or unsupported claims back into research.
  • Test beyond the development briefs. Repeat unseen tasks, measure failure/repair cost, and compare realistic cache conditions.

Jev’s approval currently happens before retrieval. There is no post-synthesis Jev fact-check or repair loop in this controller. Moving action decisions does not, by itself, solve the writer’s grounding problem.

08 / CODE & REPRODUCTION

Where the boundaries live in code.

FileResponsibility
research.pyResearch policy, action loop, question/URL selection, argument recipes, and research checks.
jev.pyTypeSafe choice requests, response validation, retries, and controller usage.
writer.pyContent-only writing interface; rejects tool calls and empty text.
investigation.pyShared choice helper, evidence projection, observations, and standard/compact loops.
external.pyMCP connections, allowed dispatch, schema validation, timeout, and truncation.
measurement.pyPer-call LLM usage, tokenizer-based schema estimates, and totals.
benchmark.pyRuns the three arms, rotates order, saves traces, evaluates, and reports paired results.

The adapter is intentionally specialized. It knows how these four tools accept queries and URLs, and which parameters can be fixed in code. Discovering an arbitrary new MCP tool does not automatically teach the controller to construct its arguments without exposing schemas to the writer.

Run the research comparison

From the repository root, with the existing model credentials in .env:

uv sync --locked --extra benchmark --group dev

# New output directory; invokes both model providers.
uv run --extra benchmark jevex-benchmark \
  --suite research --output benchmarks/runs/my-research

# Narrow to one brief, optionally repeating it.
uv run --extra benchmark jevex-benchmark \
  --task webb-hubble --repeats 2 \
  --output benchmarks/runs/my-webb-comparison

# Rebuild a saved report without model calls.
uv run --extra benchmark jevex-benchmark \
  --summarize benchmarks/runs/my-research

Output directories must be new. Live execution incurs model usage and depends on external services. No credentials are embedded in this page. Research does not require the optional repository checkout.

Inspect the evidence

results.json stores answers, checks, tokens, and elapsed time. Per-run JSONL files record model messages, choices, tool arguments, and delivered observations. catalog.json captures schemas; metadata.json records models, limits, hashes, and dependency versions. Raw traces can contain source data and local paths, and are Git-ignored.

The finding in one sentence: a structured controller can keep tool orchestration out of the writing model and materially reduce its token traffic, but useful research still depends on evidence coverage, grounded synthesis, and the cost of the controller itself.
